## Auth/session contracts

- Native auth uses Clerk after a session exists.
- Protected feature calls require authenticated user context and must handle session expiry gracefully.
- Mobile OAuth can return a one-time 128-char hex `MobileSession` token. Prefer the URL fragment (`#token=`) over the query string.
- Native stashes the token in module memory (not MMKV), then:

  1. `POST /api/mobile/exchange` with `{ token }` (or `Authorization: Bearer <token>`). No Clerk session required.
  2. Receive `{ ticket, expiresAt }`.
  3. `signIn.create({ strategy: 'ticket', ticket })` then `setActive({ session })`.

- A second exchange of the same token fails. If exchange returns 404/401, leave the user on login.
- After a Clerk session exists, login can also use Google, Apple, email/password, and MFA. Those are Clerk strategies, not extra API routes.
- `GET /api/user/check-username?username=` is the public handle-availability check.

## Quest and reward API contracts

- Quest progression is backend-authoritative for eligibility and completion.
- Daily quiz sessions use `/api/v1/engage/quests/{questId}/session`, `/session/{sessionId}/submit`, and `/session/{sessionId}/forfeit`.
- Arena check-in is `POST /api/v1/engage/quests/arena-check-in` (once per team per UTC day).
- Reward claim/redeem behavior must use server responses as truth for user-facing state.
- Pass-related gating (global/event) is evaluated server-side and reflected in client rendering.

## Apple Wallet and App Clip contracts

- Add a pass to Apple Wallet with `POST /api/v1/passes/apple-wallet` and a Clerk bearer token. Send `{ "passKind": "fan_id" | "club_membership" | "arena_event", "teamId"?, "gameId"?, "format": "base64" }` then decode `data.pkpassBase64` to bytes, build a `PKPass` from that `Data`, and present it with `PKAddPassesViewController`. `club_membership` needs the `teamId` of an Engage partner club the fan has joined; a non-partner club or an unjoined club returns `403`. Unknown body fields return `400`.
- Treat `503 CONFIGURATION_ERROR` from the pass route as "Wallet passes not available yet" and hide or disable the add-to-Wallet entry point.
- The iOS App Clip (`LU58V6484P.com.dsports.wallet.beta.Clip`) is invoked on `https://app.d-sports.org/clip/arena/<id>`, where `<id>` is a game event ID, team ID, or team slug. Apple reads the association file from the invocation host, so `app.d-sports.org/.well-known/apple-app-site-association` must serve the API's AASA (via the engage-native Vercel rewrite). That file lists `/clip` and `/clip/*` under `applinks` and the clip under `appclips`.
- The App Clip loads its card from `GET /api/v1/app-clips/arena/{id}` without auth. Send the last `ETag` as `If-None-Match`; you get `304` only while it still matches the current card. A `404` means the ID matches no game or club.
- The preview never checks a fan in. When `checkInAvailable` is true, hand off to `fullAppUrl` (or sign in) and call `checkInEndpoint` (the authenticated arena check-in above) with `{ "teamId": team.id }` from the preview. For a game event, `team` is the home club, so do not send the game ID from the URL.

## Fan Rep contracts

- `GET /api/v1/engage/rep/breakdown` returns Fan/Club/Player/Direct totals plus `clubRepByTeam`. `dsportsDirectRep` sums `repType = Direct` rows.
- `GET /api/v1/engage/rep/ledger` is keyset-paginated. `source` is `fanAmp` | `club` | `playerAmp` | `dsportsDirect`.
- `POST /api/v1/engage/rep/earn` accepts only `reaction`, `message`, `pollVote`, and `share`. Amount and `repType` are server-authoritative. Direct kinds return `403`.
- Do not call `/earn` for arena check-in, daily-quest completion, or admin Direct grants.
- Direct grants use `POST /api/admin/users/{userId}/rep` (`isAdmin` only). Native Coins UI for this is follow-up.

## Team and league API contracts

- Team lists and team metadata come from `/api/teams`. Use `?slug=` for a single team, or public `GET /api/teams/{id}` when you have an id or slug (id is tried first). Archived teams return `404`.
- `GET /api/teams/search` accepts `q`, `sport`, `league`, `cursor`, `limit`, and `sort` (`rank` | `name` | `fans`).
- Team list, detail, and search payloads include `nickname`, the admin-set short club name, or `null`. Pass it to `formatTeamName(team, "name_only")`, which already prefers a non-blank `nickname` over derivation. The API port of that derivation is `lib/team-short-name.ts`; keep the two in step.
- Sports chips come from public `GET /api/config/sports`. On `500`, fall back to a local cache. Do not hardcode a second catalog.
- Team `sport` and `leagueInfo.sport` are never null. Unknown values are `"other"`.
- `POST /api/teams/{id}/follow` is social only (`TeamFollow`).
- `POST/DELETE /api/teams/{id}/join` is leaderboard membership only. Both are idempotent.
- HQ stars are bookmarks, not follows. `GET /api/me/starred-teams` lists them. `PUT` and `DELETE /api/me/starred-teams/{teamId}` star and unstar. Optional `PUT` body `{ slug?, name?, logo? }` stores a display snapshot. A new star past 50 clubs returns `409 STARRED_TEAMS_LIMIT`. `POST /api/me/starred-teams` is the one-time additive merge (`skipped` and `rejected`, not a hard failure).
- `GET /api/user/teams` returns `{ joinedTeamIds, followedTeamIds }`.
- `GET /api/teams/{id}/roster` is public and returns `{ players }` for the formation builder. Read optional `photo` and `availability` on each player. `availability` is omitted when the player is available.
- League metadata and branding come from `/api/leagues`.
- `GET /api/leagues/{leagueId}/standings` is public HQ standings. `leagueId` is the Prisma id or slug. The response is `{ rows, tiebreakRules, tables }`. `rows` is one team each. `tables` lists every remaining scope. Empty `rows` mean the league cannot be scored honestly.
- Call `GET /api/teams/{id}/head-to-head?opponentId=` for the public series. You get `{ record, meetings }` for the five most recent decided meetings. Omit `opponentId`, or send the same id as `{id}`, and you get `400`.
- Synced canonical data changes can propagate asynchronously; client should tolerate short-lived staleness.

## Binder PIN contract

- Binder PIN is not the wallet PIN and not `POST /api/v1/user/verify-pin`.
- `POST /api/binders/{id}/verify-pin` returns `{ granted, token, expiresIn: 300 }`.
- Send `token` as `x-binder-pin-token` on `GET /api/binders/{id}`.
- Missing or expired proof on a PIN binder returns `403 PIN_REQUIRED` with metadata only (no shelves).

## Locker room authoring

- `teamId` on `POST /api/locker-room` is the about-tag.
- `authorTeamId` / `postAsTeamId` is who the post is authored as. Unauthorized callers get `403`.
- `lineup` on create is persisted and echoed. Fetch players from `GET /api/teams/{id}/roster` instead of fabricating names.
- Composer drafts use `GET/PUT/DELETE /api/locker-room/posts/draft`.
- `POST /api/locker-room/{id}/like` returns `{ liked, likeCount }` and does not replace `/react`.
- Comment create may send `mentionedUserIds`. Responses include `mentions[]`. Edit must send `mentionedUserIds: []` to clear mentions; omitting the field leaves existing mentions in place.
- For mention typeahead, call `GET /api/user/search?q=...&scope=mention&limit=6`. Read `profileUrl` for the avatar. `handle` is a non-empty string on that scope.
- Tapping `@handle` opens that fan's profile.

### Shared videos

On iOS and Android, the share target stages a local video file and opens the Locker Room composer. Sharing does not publish the draft.

On publish, use [the direct upload flow](/repositories/d-sports-api/social-locker-room/behavior#direct-video-uploads) for native video files up to 50 MiB. Keep the Clerk token on the API calls only. Add the finalized video URL and any extracted thumbnail URL to the existing post body. Do not attach a placeholder as a thumbnail.

## Marketplace contracts

- Prefer `GET /api/v1/marketplace/me/listings`. `GET /api/v1/marketplace/listings/mine` is a native alias for the same handler. Create listings with `x-listing-pin-token`.
- Listing a `processing` pack returns `409 PACK_NOT_LISTABLE`.
- `GET /api/v1/cards/{id}/provenance` is public ownership / sale / mint history.
- Treat `GET /api/user/packs` status as the per-purchase source of truth.

## Games catalog contract

- `GET /api/games/catalog?teamId=...` (or `?teamSlug=...`) is public and returns the team's enabled mini-games grouped by cadence: `{ daily: Game[], weekly: Game[] }`.
- Each game entry carries `id`, `key`, `title`, `description`, `icon`, and `badge`; `key` is the stable slug the client maps to a playable game route (for example `daily-spin`).
- The catalog is admin-managed and team-selected server-side; the client must render only the games returned and must not assume a fixed set.
- Responses are cacheable (`Cache-Control: public, max-age=60, stale-while-revalidate=300`); short-lived staleness after a team changes its selection is expected.
- Unknown teams return `404`; a missing `teamId`/`teamSlug` returns `400`.
- Native also calls `GET /api/v1/engage/games/catalog` and joins the two lists. Engine session verbs, HUD rules, and update-required behavior live in [Game Engine](/repositories/game-engine/index). Do not ignore unknown engine keys.
- `locker-singularity` does not use session verbs. Read and mutate `/api/v1/engage/games/locker-singularity/ledger`. Send `X-Client-Version`. Mutations need a UUID `idempotencyKey` the client already holds. Send tap counts, never buzz values. Boost claim stays `410 BOOST_DISABLED`.

## Game Center contracts

- `GET /api/events/schedule` accepts repeatable `teamId` query params.
- `GET /api/events/realtime` is public Broadcast discovery. Event detail includes a `realtime` pointer without the anon key.
- Use the public Game Center reads under `/api/events/{gameId}` for detail, box score, player-stats, plays, lineup, top-performer, and win-probability. Top-performer sides include `playerKey` (same key space as `LineupSlot.playerKey`) and `playerId` (linked roster id, or null).
- Chat mute is `POST/DELETE /api/events/{gameId}/chat/mute` with either `userId` or `thread: true`, not both.
- Ratings submit is `POST /api/events/{gameId}/ratings`. Do not also call `/api/v1/engage/rep/earn`.
- Call `POST/DELETE /api/events/{gameId}/live-activity` to register or end an iOS Live Activity. You must have `UserSettings.liveScoreUpdates` consent first.

## User mute and block

- Global mute is `GET/POST/DELETE /api/user/mutes`. One-way hide; the muted user is not notified.
- Global block is `GET/POST/DELETE /api/user/blocks`. Stronger than mute; excluded from the blocker's social surfaces.
- POST body uses `mutedUserId` / `blockedUserId` (or `handle`). DELETE accepts the same id as a query param or in a JSON body.
- Do not confuse these with Game Center thread mute (`/api/events/{gameId}/chat/mute`).

## Wallet contracts

- Custodial create: `POST /api/wallets` with `{ pin, legalTermsVersion }` only.
- Import/link: same route with `pin`, `address`, and `encryptedPrivateKey` or `privateKey`. `pin` is required on every create path.
- Custodial send: PIN gate, then `POST /api/wallets/{address}/sign-transaction`.
- Seed reveal: PIN-gated `POST /api/wallets/{address}/export`.
- Do not call deprecated `POST /api/wallets/private-key` for new work.
- Attestation is `GET /api/wallets/{address}/attestation`. The path segment is the wallet database id, not the on-chain address.
- `DELETE /api/wallets` needs `{ address, pin }` for custodial wallets. External links need `{ address }` only. Missing or wrong PIN returns `400 VALIDATION_ERROR`.

## Featured collectibles

- `GET /api/user/featured-collectibles` is public.
- `PUT /api/user/featured-collectibles` replaces the authenticated user's showcase (max 12).

## 3D pack opening

- Use the pack ID with `GET /api/packs/{id}/opening-manifest`. Pass the host's supported scene level as `?scene=3` for a v3 host. See [opening manifest behavior](/repositories/d-sports-api/collectibles/behavior#opening-manifest-and-backdrop) for accepted levels and the meshopt fallback.
- Use `data.backdropColour`: `tier` means rarity colours, `neutral` means neutral grey, and an absent key falls back to rarity colours. The server resolves pack overrides and team defaults.
- Revalidate with the manifest ETag. A change in the resolved colour doesn't change `assetVersion` or the scene protocol.
- Render the summary from `data.packSummaryLayout` in user settings, independently of the manifest backdrop. Treat an absent layout as `auto` for older servers. See the [settings contract](/api-reference/domains/auth-onboarding#pack-summary-layout) for values and PATCH behavior.

## Card display fields

Pack open, `GET /api/user/packs/opened`, `GET /api/user/collectibles`, and `GET /api/binders/{id}` cards carry `finish` and `cardTemplate` side by side.

- `finish` is a card finish id, or `null` when the card has none.
- `cardTemplate` is `{ key, version }` naming the render template behind the card's current image, for example `{ "key": "card-front-epic-holo", "version": 1 }`.
- `cardTemplate` is `null` unless the image came from a published render that still matches the stored image. It is additive and read-only, with no allowlist or kill switch.
- Treat an unknown `cardTemplate.key` as display metadata only; the card image URL is already the rendered front.

## User interests contract

- `User.interests` is a `string[]` of slug IDs stored on the `User` row in Postgres (via Prisma).
- Allowed slugs: `hockey`, `basketball`, `football`, `soccer`, `baseball`, `esports`, `gamification`, `stats`, `fan_engagement`, `collectibles`, `gambling`, `crypto`, `blockchain`, `fantasy_sports`, `live_events`, `merch_fashion`, `streaming`.
- Native onboarding step 3 and the retroactive `/(onboarding)/interests` screen require **at least one** interest before continue.
- `PATCH /api/user` accepts `interests: string[]`; server validates slugs and dedupes (max 20).
- `GET /api/user` returns `interests` on the authenticated profile payload.
- Retroactive gate: users with `onboardingComplete=true` and empty `interests` are redirected to `/(onboarding)/interests` until at least one interest is saved.

## Settings and notifications

- `GET/PATCH /api/user/settings` is the settings SoT. `privateProfile` mirrors `isPrivate`.
- Persist `notifyTeams`, `notifyMilestones`, and `notifyCommunity` as separate booleans. Do not collapse them.
- Inbox types include `GAME_ALERT` and `RATING`.

## Error handling and fallback UX

- Show user-actionable errors for purchase/open/claim/sign failures.
- Avoid silent failures for mutation endpoints.
- Use retry/backoff for transient network failures; avoid retry storms on authorization or validation errors.

## iOS widget refresh

On iOS, PR #1453 fetches `GET /api/v1/widgets/snapshot` with a scoped widget bearer.
The app mints it with Clerk auth via `POST /api/v1/widgets/token`.
The token mint body includes `deviceId` (a stable per-install ID) and `platform: "ios"` per the [Widget API contract](/api-reference/domains/platform-infra#widget-api).
These fields apply only to token minting, not snapshot fetching.
The app shares the bearer through the App Group Data Protection Keychain.
Non-secret metadata lives in App Group UserDefaults.

The patched `expo-widgets` AppIntent/timeline refresher calls the snapshot endpoint without JS.
The host JS provider selects a cached Clerk JWT only when the Keychain read returns no token.
A 401/403 clears the native token.
The host JS provider does not retry that request with Clerk.
ETags are per target.
HQ 304 freshness checks game identity.
Expired tokens and 401/403 responses cause credential deletion.
These failures mark cached data stale.
Missing credentials skip fetch.
Offline/server failures retain stale data.
Sign-out/account changes attempt revocation.
They wipe local credentials, validators, and timelines.

During an HQ refresh, an explicit `hqLive: null` idles an active live card.
It preserves a retained final card.
A rank refresh does not perform this idle reset.
See [iOS widget configuration](/repositories/d-sports-engage-native/architecture#widget-controls-and-interaction-configuration) for cadence, rebuild requirements, and test limits.
Android's file storage, WorkManager, backoff, and total JS timeout budget below do not describe iOS.

### Google Wallet

Use the existing [Platform API](/api-reference/domains/platform-infra) and [Platform behavior](/repositories/d-sports-api/platform-infra/behavior#pass-issuance-and-widget-refresh) for authentication, responses, and server errors. For a `fan_id`, omit the body. For `club_membership`, send the `teamId` (ID or slug) of an Engage partner club the fan has joined. Any other club is forbidden. For `arena_event`, send a `gameId` or `teamId` to scope the pass, or omit both for a general pass. The shipped Android client from PR #1421 uses `walletPass.issueGoogleWalletPass` in `lib/api/wallet-pass-api.ts`; it does not generate or sign passes. Saving an event pass does not check the fan in.

`hooks/use-google-wallet-pass.android.ts` hands the signed JWT to the Pay API through `lib/google-wallet/native.android.ts`. If native availability is false or saving returns `unavailable`, it opens the server Save URL through `Linking.canOpenURL`/`openURL`. The wrapper accepts only a nonempty suffix after `https://pay.google.com/gp/v/save/`. Do not cache or log the JWT or Save URL. Native cancellation does not trigger fallback; native errors show error feedback. Browser opening does not prove saving, and only native `saved` updates the mounted hook's added state.

An explicit `503 CONFIGURATION_ERROR` hides the CTA for that mounted hook and shows localized configuration feedback. Transient `503 RATE_LIMITER_UNAVAILABLE` and other errors leave it available and show an error. The button is signed-in Android only; missing native support retains browser fallback, while iOS/web stubs no-op. There is no persistent membership check or automatic pass-update integration. See [Google Wallet configuration](/repositories/d-sports-engage-native/architecture#google-wallet-pass-configuration) for native dependencies and rebuild requirements, and [entry points](/repositories/d-sports-engage-native/feature-mapping#google-wallet-passes) for all three pass kinds.

### Widget refresh

Android refresh uses `GET /api/v1/widgets/snapshot` with the stored scoped widget bearer; the JS auth provider falls back to the unexpired cached Clerk bearer. The mounted `useAndroidWidgetTokenSync` hook ensures an installation token on sign-in/account changes and app foreground. Sign-out/account-switch cleanup attempts server revocation and clears native credentials, validators, snapshots, and WorkManager jobs. Token storage is Android Keystore-encrypted under `noBackupFilesDir/widgets/widget-token.enc`. Follow the existing [widget API](/api-reference/domains/platform-infra#widget-api) and [backend snapshot behavior](/repositories/d-sports-api/platform-infra/behavior#widget-snapshot) for issuance, authorization, response fields, caching, and errors (d-sports-api #1180; docs #327).

`lib/widget-snapshot-api.ts` and native `WidgetSnapshotApiParser` unwrap `{ success, data }` and consume nested home/away scores, slug, colors, HTTPS logos, last-play text, squad label, and the HQ app deep link. Missing decorations fall back only to the same cached game, then defaults. Per-target ETags support 304 revalidation; HQ freshness also requires the validator's game ID to match stored data. Failed refresh retains data and marks it stale. The JS fallback shares a four-second budget across auth lookup, fetch, and JSON parsing. Native 401/403 clears credentials and validators for re-minting on foreground; 429 records Retry-After backoff. Refresh does not navigate through sign-in or bypass server authorization.

An explicit `hqLive: null` differs between refresh paths. Native `WidgetSnapshotApiParser` parses it as a present, empty HQ result. For an HQ-targeted refresh, `WidgetRefreshCoordinator` writes a fresh versioned snapshot with `game: null`, replacing the previously cached game and clearing the failure marker on a successful write. Kotlin still merges the separate push snapshot at render time. The JS path in `lib/widget-refresh.android.ts` instead retains the cached HQ game and its current stale state, returns `refreshed: false`, and records the response validator with `hqGameId: null` on HTTP 200. Do not interpret that JS result as a newly fetched live game.

`lib/widget-contract.ts` defines the local versioned contract: `schemaVersion: 1`, `kind` (`rank` or `hq_live`), `producedAtMs` (data age), `source` (`app`, `push`, or `api`), `stale`, optional `staleAtMs`, payload, and localized `copy`. JS screen-owned writers serialize at most 4 KB through a temporary file and move to `filesDir/widgets/<kind>.v1.json`; serialization/size failures skip the write. Native API refresh writes the same versioned files. Kotlin merges these with separate push snapshots at render time. This is a client storage contract, not an additional backend endpoint.
