## Main non-admin routes

- `GET /api/packs`
- `GET /api/packs/[id]`
- `POST /api/packs/[id]/purchase`
- `POST /api/packs/[id]/open`
- `GET /api/packs/[id]/opening-manifest`
- `GET /api/packs/[id]/odds`
- `GET /api/user/packs`
- `GET /api/user/packs/opened`
- `GET /api/user/collectibles`
- `GET/PUT /api/user/featured-collectibles`
- `GET/POST /api/binders`, `GET/PATCH/DELETE /api/binders/[id]`
- `POST /api/binders/[id]/verify-pin`
- `GET /api/v1/cards/[id]/provenance`

## Runtime behavior highlights

- Pack browse routes expose currently available packs and pack metadata.
- `POST /api/packs/[id]/purchase` starts a purchase. `PUT` on the same path always returns `410 GONE`. Confirmation moved to `POST /api/checkout/crypto/verify`.
- Purchase start records pack purchase state for the user. Free packs are limited to 3 purchases per user per UTC day.
- Open route resolves collectible outcomes and updates user ownership/inventory state.
- `GET /api/user/packs` status is authoritative (`pending` | `processing` | `opened` | `completed`). Template `isOpenable` is not per-purchase state.
- User collectible and pack routes expose owned content for client rendering.
- Featured collectibles expose a public showcase; authenticated replace is capped at 12 slots.
- Binder routes (`/api/binders*`) are in the generated OpenAPI. Cover upload is `POST /api/upload/binder-cover`.
- PIN binders require `x-binder-pin-token` from verify-pin. Without it, `GET /api/binders/[id]` returns `403 PIN_REQUIRED` and metadata only.
- `GET /api/v1/cards/[id]/provenance` is public and returns `{ card, currentOwners, transfers, mints }`.

## Opening manifest and backdrop

The optional `scene` query parameter is the client's supported scene level (an integer from 0 to 99). The server treats an invalid value as absent. For meshopt templates, a missing or insufficient level returns `data.template: null` and `data.sceneEligible: false`.

The public manifest looks up the pack template by ID, not the fan's purchase. It returns the optional `data.backdropColour` from the pack override, then the team default. An explicit `tier` on the pack overrides a `neutral` default. When both values are unset, the server omits the key and clients fall back to rarity colours.

The backdrop does not change the pack art, draw, or `assetVersion`. Changes to the resolved colour do change the full-manifest ETag, so revalidate the manifest with `If-None-Match` rather than relying on `assetVersion` to detect colour changes. A matching tag returns `304`. The CDN uses `s-maxage=60, stale-while-revalidate=300`, so edits may not appear immediately.

## Card display fields

Pack open (including replays), `GET /api/user/packs/opened`, `GET /api/user/collectibles`, and `GET /api/binders/[id]` cards carry `finish` and `cardTemplate` side by side.

- `finish` is a card finish id, or `null` when the card has none.
- `cardTemplate` is `{ key, version }` naming the render template behind the card's current image, for example `{ "key": "card-front-epic-holo", "version": 1 }`.
- `cardTemplate` is `null` unless the image came from a published render that still matches the stored image. It is additive and read-only, with no allowlist or kill switch.
- Card fronts come from ten v1 templates chosen by rarity: Common `contour`; Rare `sidebar`; Epic `facet`, `holo`; Legendary `arch`, `burst`, `rail`; Mythic `aurora`, `eclipse`, `rays`. Keys are `card-front-<rarity>-<name>`.

## Side effects and dependencies

- Purchase/open flows may integrate with checkout, wallet, and minting subsystems.
- Historical fix/backfill scripts exist for pack purchase and rarity correction scenarios.

## Known caveats

- Deterministic guarantees depend on pack configuration integrity and weighted content setup.
- Open and purchase flow state transitions can require reconciliation in rare partial-failure cases.

## Exclusions

- Admin collectible/pack creation and stock management flows are excluded.
